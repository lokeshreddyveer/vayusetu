# ADR-011: Local DNS tunnel and Protection Coordinator

Status: Proposed. Date: 2026-10-12. Supersedes the standalone-DNS-profile design in the v1.3 documents (NEDNSSettingsManager "DNS Only").

## Decision

DNS Only is a user-authorized local packet tunnel owned by VayuSetu. It needs no imported VPN profile, no remote server and no standalone iOS DNS profile. Users bring their own VPN configurations (WireGuard first). iOS runs one personal packet tunnel at a time, so exactly one tunnel owner exists:

- Off: no tunnel.
- DNS Only: local DNS tunnel. Only the virtual DNS address is routed into it; ordinary traffic is not captured.
- VPN Only / VPN + DNS: the active VPN runtime owns the tunnel. DNS filtering runs inside that runtime where the adapter allows it. A second tunnel is never started.

Safari content blocking is independent of tunnel mode. A serialized ProtectionCoordinator (Swift actor in the app) resolves policy, performs tunnel handoffs and publishes per-surface observed state. The extension receives versioned configuration snapshots over an App Group plus provider messages and acknowledges the applied revision. The full architecture text is the product specification; this ADR records the decision and the gap below.

## Operating modes

Three independent user controls give eight primary modes: VPN profile (off/on) x DNS protection (off/on) x Safari blocking (off/on). Everything Off; DNS Only (local tunnel); VPN Only; VPN + DNS; Safari Only; DNS + Safari; VPN + Safari; VPN + DNS + Safari. VPN + DNS needs an adapter that can host the DNS engine (WireGuard candidate; IKEv2 reports Limited). Internally DNS has two dimensions, the engine (encrypted DoH/DoT resolution) and filtering (local rules), so encrypted DNS with no blocklists is valid. These are sub-policies, not extra tunnels: resolver source (VPN-provided or selected), upstream route (inside or outside the VPN where the adapter can enforce it), strict vs explicit-fallback, timed pause of filtering, per-network preferences.

| Coordinator actor | Missing. Mode logic is spread across `AppStore` (`changeDNSMode`, `connectSelected`) and the `@MainActor` `TunnelController`. |

## Feasibility risks to settle before building on this

1. DNS Only routing: the tunnel sets a virtual DNS server address with `includedRoutes` limited to that address, parses UDP/TCP DNS from `packetFlow`, and forwards over DoH/DoT on sockets that are not routed back into the tunnel. Needs device proof of no routing loop, IPv6, DNS64/NAT64 and captive portals.
2. Apps that use their own DNS or hardcoded resolver IPs bypass a DNS-address-only route. Capturing all port-53 traffic requires wider routes and is a different trade-off.
3. VPN + DNS inside WireGuard is the hardest item. The WireGuard adapter hands the utun to wireguard-go, so Swift never sees packets. Local filtering needs either a patch to the vendored Go backend (intercept DNS to the tunnel DNS address) or a userspace DNS responder reachable at that address. Until then VPN + DNS is reported Limited, as today.
4. IKEv2 (system-managed) cannot host local filtering. It stays Limited by design.
5. Distribution: the local-tunnel use of the packet-tunnel entitlement must be acceptable for App Store review. The privacy-policy URL and review notes belong with the open App Store decisions.
6. Handoff DNS Only to VPN is a real interruption (stop one tunnel, start the other). Do not claim seamless switching.

## Acceptance evidence

The 13 acceptance tests in the architecture text, run on a physical device. No feature is complete on a passing mock or a built screen. Existing evidence rules apply: a connected tunnel or a resolver probe is not verified protection.

## Spike status (2026-10-12)

Built, signed and installed on the paired iPhone (iOS 0.11.2, build 18 plus the spike); not yet exercised on the device. Code: `ios/Tunnel/DNSOnlyRuntime.swift` (inside the existing tunnel extension, selected by `TunnelSecret.runtime == "dnsOnly"`), `TunnelController.connectDNSOnly`, and a "Local DNS tunnel (experimental)" section on the DNS tab. 46 host checks pass for the packet codec, SERVFAIL fail-closed answer, DoT/DoH framing and bootstrap validation. Those checks are not device evidence.

Design as built: virtual DNS server 198.18.0.2 with the only included route being that /32; no default route, so ordinary traffic is not captured. Upstream DoT/DoH connects to bootstrap IPs with the resolver hostname as TLS server name, so resolving the resolver never re-enters the tunnel. Upstream failure returns SERVFAIL; there is no plaintext fallback.

Known gaps against the full requirements: IPv4/UDP only (no TCP DNS, no IPv6 transport, no fragment reassembly); fixed virtual address with no collision check against the current network or other VPN routes; a fresh TLS connection per query (no reuse, cache or EDNS handling beyond pass-through); no local rule matching or block responses; counters are in memory and reset with the extension; no NWPathMonitor-driven recovery; the old system-DNS path is still in the UI.

Device checks that decide whether to proceed: (1) iOS prompts for VPN permission and the tunnel reaches Connected; (2) browsing and apps still work; (3) the "Queries answered" counter rises while browsing, and answers resolve through the selected resolver; (4) stopping the tunnel restores normal DNS; (5) survives backgrounding and a Wi-Fi/cellular switch; (6) the packet-tunnel entitlement is acceptable for App Store review (TestFlight is the first signal).

## VPN engines and the "bring your own config file" goal

Filtering needs VayuSetu to see the packets, so it can only run inside engines VayuSetu itself hosts in its packet tunnel. Status: WireGuard hosts it today (Go filter wrapping the tun device, `dnsfilter.go`, falls back to no filter when not configured); the local DNS tunnel hosts it (Swift). Apple's system IKEv2 (`NEVPNManager`) is OS-run and cannot host it. OpenVPN and a self-hosted IKEv2 need an embedded engine, and the realistic engines are copyleft or commercial: OpenVPN3 (AGPLv3 or a commercial licence from OpenVPN Inc.), strongSwan (GPLv2). Decision needed before building: (a) release VayuSetu under a compatible open-source licence, (b) buy a commercial OpenVPN licence, or (c) stay with WireGuard plus native IKEv2 (no filtering on IKEv2). Once an engine is chosen, an engine that reads packets through `NEPacketTunnelFlow` plugs into the existing Swift interceptor (`DNSOnlyRuntime.handle`), and its `.ovpn`/IKEv2 files are imported as profiles like WireGuard `.conf` files.

## Proposed order

1. Device feasibility spike: minimal local DNS tunnel (no UI changes) answering and forwarding DNS over DoH, plus a negative control that ordinary traffic is not captured.
2. Coordinator actor, config revisions and App Group snapshots, wrapping the current WireGuard path unchanged.
3. DNS Only on the spike runtime; retire the NEDNSSettingsManager path behind a migration.
4. DNS-side rule matcher fed by FilteringCore (reuse `FilterRule`, `RuleEngine`), cache, DoT, statistics.
5. VPN + DNS inside WireGuard (risk 3).
6. Package extraction and hardening.
